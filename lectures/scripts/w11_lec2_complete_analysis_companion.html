Section 3 — _quarto.yml · 0:22–0:35

TipInstructor cue · Slides 6–7 · 13 min

Return to the slides briefly for Slide 6, then come back here and open the _quarto.yml file you prepared before class alongside this document in RStudio. Show its contents without going deep into syntax. The concept: one file at the root, shared settings, navbar appears on every page.

End this section by pointing to the course website: “This site — nceas-learning-hub.github.io/sfsu_data_sci — is built exactly this way. Everything you see there was made with the tools you now know.”

Remind students: they do not need _quarto.yml for this week’s activity. A single index.qmd with Markdown links is completely sufficient. This is the step up for thesis projects with multiple chapters.

When you have multiple .qmd files that should all look the same — same theme, same TOC settings, same navigation bar — don’t repeat the YAML in each file. Create _quarto.yml at the root of your project and Quarto applies it to every document automatically.

# _quarto.yml — place this file at the root of your project

project:
  type: website

website:
  title: "My Research Project"
  navbar:
    left:
      - href: index.qmd
        text: Home
      - href: analysis/data-cleaning.qmd
        text: Data Cleaning

format:
  html:
    theme: cosmo
    toc: true

What _quarto.yml unlocks · Slide 7

With _quarto.yml and type: website, your repository becomes a proper multi-page site:

  • A navbar that appears on every page automatically
  • Shared theme, font, and layout across all documents
  • quarto render in the Terminal builds every page at once
  • quarto preview lets you see the full site locally before pushing
NoteYou don’t need this for today’s activity

A single index.qmd with Markdown links is enough for the current assignment. _quarto.yml is for thesis projects with multiple chapters and a consistent navigation structure across all pages.

Connecting this to your thesis · Slide 8

Here is one way to structure a thesis GitHub repository so it publishes cleanly to GitHub Pages:

thesis-project/
├── _quarto.yml                 ← shared settings and navbar
├── index.qmd                   ← project overview and data description
├── analysis/
│   ├── 01-clean.qmd            ← data cleaning decisions, documented
│   ├── 02-explore.qmd          ← exploratory analysis
│   ├── 03-model.qmd            ← statistical modeling
│   └── 04-figures.qmd          ← publication-ready figures
├── data/                       ← raw data (or link to repository)
└── figs/                       ← saved figure outputs

Your committee sees a URL. Your advisor can open it without installing R. Your collaborator at another institution can check your work. Six months from now, you can pick this up and understand what you did — because you documented it.

Who is your audience? · Slide 9

Different audiences need different things from your site:

Advisor: Can they trace your logic from raw data to conclusion? Is the decision log visible?

Collaborator who doesn’t use R: Can they see the visualizations and read your interpretations without running anything?

Future you: Can you pick this up in six months and understand what you did and why?

The site forces you to write for all three.

Open science in practice · Slide 10

Many journals now request or require: data availability statements, analysis code shared openly, and reproducible workflows. A GitHub Pages site with your Quarto analyses satisfies all three. Some journals link directly to your GitHub repo or your published site in supplementary materials.

You are not learning a tool. You are building a practice.

Section 5 — Troubleshooting · 0:47–0:55

TipInstructor cue · Slide 11 · 8 min

Work through the three issues below. After presenting them, ask in Zoom: “Is everyone’s site live? Thumbs up if yes.” Flag any non-responders — they may need help before Thursday.

Keep this section brisk. The goal is to send students into Thursday with working sites, not to cover every possible failure mode.

Three issues come up almost every time:

1 — Site shows “404” or won’t load

  • Is index.html committed and pushed? Not index.qmd — the HTML file is what GitHub Pages serves.
  • Did you activate Pages in Settings → Pages → Branch: main → Folder: root → Save?
  • After pushing, wait 2 minutes and hard-refresh (Cmd+Shift+R on Mac, Ctrl+Shift+R on Windows).
  • Try the URL in a private/incognito window first — browsers cache aggressively.

2 — Link goes to .qmd instead of .html

<!-- Wrong — links to the source file -->
[See the data page](data.qmd)

<!-- Right — links to the rendered file -->
[See the data page](data.html)

Render the file first, then commit the .html. The .qmd is your source. The .html is what the browser serves.

3 — Old content is still showing

GitHub Pages caches aggressively. Try the URL in an incognito window. If that shows updated content, clear your browser cache or wait a few minutes.

NoteThe order matters every time 
Render  →  Stage (add)  →  Commit  →  Pull  →  Push

Both the .qmd and the .html must be committed and pushed. The .qmd is version control for your source. The .html is what GitHub Pages publishes.

What’s next: spatial data with sf · Slides 13–14

Next week we move into geospatial analysis. The publishing workflow is identical to what you learned today — you will render analyses that produce maps and publish them to GitHub Pages. The sf unit builds directly on the foundation you have now.

The conceptual shift:

Right now, when you have location data, you have latitude and longitude columns — numbers. sf treats those numbers as geometry: points in a coordinate reference system. Once you have sf objects, you can do things that are impossible with plain columns: spatial joins, distance calculations, buffering, overlaying with polygon data.

The coordinate reference system (CRS) is what makes “spatial” different from “just numbers with labels.” The leaflet maps from the visualization unit are a preview of the spatial thinking we’ll build on next.

# sf teaser — Slide 14
# Read this, don't run it yet.

library(sf)

# A data frame becomes spatial
lobster_sf <- st_as_sf(lobster_data,
                       coords = c("longitude", "latitude"),
                       crs = 4326)  # WGS84 — the standard GPS CRS

# Now you can do spatial joins, buffering, distance calculations...
# ...and publish the result to GitHub Pages.
