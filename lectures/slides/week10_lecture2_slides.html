Git is a coordination system.

Commit A record of a decision
Branch A personal workspace with a purpose

The five-people problem

Imagine five people editing the same document at once:

Who owns what? If everyone can edit everything, nobody is responsible for anything.

What if two people change the same sentence? Both versions exist — who decides which is right?

How do you know what changed? Without a record, you cannot trace a decision back to its source.

GitHub solves all three — but only if you use it with intention.

Main branch = the official version

main is the published version — clean, reviewed, trusted.

You do not edit main directly.

Branches are personal workspaces. Create one when you start a task. Work there safely. Nothing touches main until it has been reviewed.

The five-step branch workflow

  1. Create a branch
  2. Make your changes
  3. Open a pull request
  4. Review
  5. Merge

Everything we add today is in service of making these five steps intentional rather than chaotic.

What a pull request actually is

You are not saying:

“I changed the file.”

You are asking:

“Here is my version — should we accept it?”

A pull request is a proposal. It invites review, discussion, and a deliberate decision about whether the change belongs.

The commit is the work. The pull request is the conversation about the work.

Writing and reviewing pull requests

If you are writing a PR:

Make the case for your change. What did you do? Why? What should the reviewer look for?

If you are reviewing a PR:

Actually engage with the change. Does it do what it claims? Is there a better approach? Are there side effects?

“Looks good” is not a review.

Issues: defining the work

An issue is a defined unit of work.

  • Has a title, a description, and an assignee
  • One issue = one task
  • Specific, bounded, completable

The rule: no work without an issue.

Before you touch a file, there is an issue that describes what you are doing and why — and it is assigned to you.

This solves the ownership problem.

What makes a good issue?

❌ Too vague

“Improve the analysis”

✅ Specific and completable

“Add axis labels to the species richness plot”

“Fix the broken file path in the data loading script”

“Add a methods section to the draft report”

Project board: seeing the whole picture

Four columns track every piece of work:

Column Meaning
To Do Available — not yet claimed
In Progress Claimed — someone is working on it
In Review PR is open — waiting for review
Done Merged — issue closed

At any moment, anyone can see the full state of the project without asking anyone.

The structured workflow — ten steps

  1. Go to Issues → choose one → assign yourself
  2. Move to In Progress on the board
  3. Create a branch: issue-#-short-description
  4. Make your change — one task only
  5. Commit with a clear message
  6. Push and open a PR — write Closes #[issue number]
  7. Move to In Review on the board
  8. Partner reviews PR — leaves at least 2 specific comments
  9. Revise if needed → merge
  10. Move issue to Done

What does Closes #3 do?

In the chat: take a guess.

When the PR merges, GitHub automatically closes issue #3.

It also links the PR to the issue in the UI — you can click from one to the other.

This is the automation payoff for using issues and PRs together.

Branch naming is communication

Name your branch: issue-#-short-description

Examples:

  • issue-3-fix-readme
  • issue-7-add-axis-labels
  • issue-12-fix-data-path

The issue number in the branch name tells anyone on the team exactly what the branch is for — without asking.

Compare to: my-edits, updates, patch-1

The rules

No work without an issue Claim it before you start.

No direct edits to main Always work on a branch.

One issue per branch If you notice another problem, open a new issue.

Every PR must be reviewed before merging “Looks good” is not a review.

Three things to remember

1. Git is a coordination system, not a save button. Every branch, commit, PR, and issue is a communication tool.

2. Structure prevents chaos. Monday felt messy because there was no structure — not because the tools are hard.

3. Pull requests are conversations. Write them so the reviewer knows what to look for. Review them so the author knows what you actually looked at.
