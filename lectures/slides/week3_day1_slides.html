The Traditional Problem

Old workflow:

  1. Run analysis in R → save plot
  2. Write manuscript in Word
  3. Copy/paste plot into Word
  4. Revise analysis → new plot
  5. Copy/paste again (hope you got the right one!)
  6. Reviewer asks for change
  7. Which version of the code made THIS plot?

Problem: Code, results, and narrative are disconnected

Literate Programming Solution

New workflow:

Everything in ONE document:

- Narrative explanation

- Code that runs

- Results (plots, tables) automatically generated

- Change code → results update automatically

One file = complete reproducible analysis

No more “which version made this plot?”

What Is Quarto?

Quarto = Publishing system for data science

Creates: HTML, PDF, Word documents, presentations, websites

From: Plain text files (.qmd) with code and narrative

Evolution of: R Markdown (if you’ve heard of it)

Key insight: Write once, output to many formats

Anatomy of a Quarto Document

---
title: "Bee Diversity Analysis"
author: "Your Name"
format: html
---

## Introduction

We surveyed 45 urban gardens for bee species richness.

```{r}
#| echo: true
#| eval: false

# This code runs when you render
bees <- read.csv("data/raw/bees.csv")
head(bees)
```

The mean richness was 12.3 species per site.

Three Parts of a Quarto Document

1. YAML Header (metadata)

---
title: "My Analysis"
format: html
---

2. Narrative (Markdown text)

We found significant differences between sites.

3. Code chunks (executable R code)

```{r}
plot(x, y)
```

YAML: Document Settings

YAML = Yet Another Markup Language

Controls document appearance and behavior

Common settings:

---
title: "Water Quality Analysis"
author: "Gretchen LeBuhn"
date: "2024-01-22"
format: 
  html:
    toc: true          # Table of contents
    code-fold: true    # Collapsible code
    theme: cosmo       # Visual theme
---

Markdown: Simple Formatting

Markdown = Plain text formatting language

# Main heading
## Subheading

**bold text**
*italic text*

- Bullet point
- Another point

1. Numbered item
2. Another item

[Link text](https://example.com)

Easy to read, easy to write

Code Chunks: Where Analysis Happens

Code chunks = Executable code blocks

```{r}
#| label: load-data
#| echo: true

# This code runs when you render
bees <- read.csv("data/raw/bees.csv")
head(bees)
```

Output appears in final document automatically

Code Chunk Options

Control what appears in output:

```{r}
#| echo: true       # Show code
#| eval: true       # Run code
#| message: false   # Hide messages
#| warning: false   # Hide warnings
#| fig-width: 8     # Figure width
#| fig-cap: "Species richness by site"

plot(richness ~ site, data = bees)
```

Common combinations:

  • Show code + output: echo: true
  • Hide code, show output: echo: false
  • Don’t run: eval: false

Inline Code: Values in Text

Problem: Hardcoding values

“The mean richness was 12.3 species.”

What if data changes? Have to find and update manually.

Solution: Inline code

The mean richness was `r mean(bees$richness)` species.

Result: Value updates automatically when data changes

No more copy/paste errors!

Quarto Workflow

1. Write .qmd file

  • Narrative in Markdown
  • Code in chunks
  • Settings in YAML

2. Render (click “Render” button)

  • Code executes
  • Output generated
  • Final document created

3. Share HTML/PDF/Word file

One click = complete document

Why This Is Better

Reproducibility: Everything in one place

Automation: Change data → rerun → document updates

Transparency: See exactly what code produced each result

Collaboration: Send one file, collaborators can re-run

Version control: Track changes with Git (Week 4!)

Efficiency: No more copy/paste between programs

Common Quarto Mistakes

❌ Forgetting backticks around code chunks

❌ Wrong YAML indentation (use spaces, not tabs)

❌ Code depends on earlier running code not in document

❌ Absolute paths

read.csv("C:/Users/Me/...")  # Breaks portability!

❌ Not rendering frequently to catch errors early

Quarto Best Practices

✅ Render early and often (catch errors immediately)

✅ Use chunk labels (#| label: descriptive-name)

✅ Keep chunks focused (one task per chunk)

✅ Add narrative (explain why, not just what)

✅ Use relative paths (project portability)

✅ Set chunk options thoughtfully

✅ Comment your code (future-you will thank you)
