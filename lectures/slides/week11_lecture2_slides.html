Controlling your published output

The YAML header of your index.qmd controls how your page looks and behaves. A few high-value options:

---
title: "My Research"
author: "Your Name"
date: today
toc: true
toc-depth: 2
number-sections: true
theme: cosmo
---
  • toc: true — adds a clickable table of contents
  • theme: — changes the visual appearance
  • date: today — auto-inserts the render date

Quarto HTML themes

Quarto ships with the Bootswatch theme library. You can preview all of them at bootswatch.com.

Popular options for scientific documents:

Theme Character
cosmo Clean, modern, readable
flatly Minimal, professional
journal Slightly more editorial
lumen Light and airy
sandstone Earthy, warm

Change one word in your YAML and re-render.

Site-wide settings with _quarto.yml

When you have multiple .qmd files that should all look the same, don’t repeat YAML in each file.

Create _quarto.yml at the root of your project:

project:
  type: website

website:
  title: "My Research Project"
  navbar:
    left:
      - href: index.qmd
        text: Home
      - href: analysis/data-cleaning.qmd
        text: Data Cleaning

format:
  html:
    theme: cosmo
    toc: true

Now all pages share the same settings.

What a _quarto.yml unlocks

With _quarto.yml and type: website, your repo becomes a proper multi-page site:

  • Consistent navigation bar across all pages
  • Shared theme, font, and layout
  • quarto render builds every page at once
  • quarto preview lets you see the full site locally

You don’t need this for today’s activity — a single index.qmd with links is enough.

But for a thesis project site, this is how it’s done.

Connecting this to your thesis

Imagine your thesis project as a GitHub Pages site:

index.qmd          ← Project overview and data description
analysis/
  01-clean.qmd     ← Data cleaning and decisions
  02-explore.qmd   ← Exploratory analysis
  03-model.qmd     ← Statistical modeling
  04-figures.qmd   ← Publication figures

data/              ← Raw data (or link to repository)
figs/              ← Saved figure outputs

Your committee sees a URL. Your advisor can open it without installing R. Your methods are reproducible.

Who is your audience?

Different audiences need different things from your site.

Advisor: can they trace your logic from raw data to conclusion? Is the decision log visible?

Collaborator who doesn’t use R: can they see the visualizations and read your interpretations without running anything?

Future you: can you pick this up in six months and understand what you did and why?

The site forces you to write for all three.

Open science in practice

Many journals now request or require:

  • Data availability statements
  • Analysis code shared openly
  • Reproducible workflows

A GitHub Pages site with your Quarto analyses satisfies all three.

Some journals will link directly to your GitHub repo or your published site in the supplementary materials.

You’re not just learning a tool. You’re building a practice.

Troubleshooting GitHub Pages

Site shows “404” or won’t load:

  • Is index.html committed and pushed?
  • Did you activate Pages in Settings → Pages → main → root?
  • Wait 2 minutes and hard refresh

Link goes to a .qmd instead of .html:

  • Your link must point to the rendered .html file
  • Render the file first, then commit the .html

Old content showing:

  • GitHub sometimes caches aggressively
  • Try the URL in a private/incognito window

From coordinates to geometry

sf objects go further:

library(sf)

# A data frame becomes spatial
lobster_sf <- st_as_sf(lobster_data,
                       coords = c("longitude", "latitude"),
                       crs = 4326)

# Now you can do spatial joins, buffering, and more

The coordinate reference system (CRS) is what makes “spatial” different from “just columns with numbers.”
