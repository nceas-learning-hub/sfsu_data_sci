You already know the four join types

In Week 5 we covered:

  • Inner join — only rows with matches in both tables
  • Left join — all rows from the left, matched rows from the right
  • Right join — all rows from the right, matched rows from the left
  • Full outer join — all rows from both, NAs where no match

Today’s question is not what are the join types?

Today’s question is: how do you decide which one to use — and how do you know if it worked?

Why does data live in multiple tables?

This is not a limitation. It is a design decision.

Separating data into tables means:

  • Each table describes one kind of thing (observations, sites, species)
  • Information is recorded once, not duplicated across rows
  • Tables can be updated independently
  • Relationships between entities are made explicit

A join is not “fixing” a problem. It is making a relationship explicit for a specific analytical purpose.

Bird surveys from parks in the central Arizona-Phoenix metropolitan area

Entity-Relationship diagrams

An ER diagram is a compact map of how tables connect.

Before writing any join code, read the ER diagram first.

Four steps to build one:

  1. Identify entities → one box per table
  2. List variables → mark primary and foreign keys
  3. Draw relationships → label with a verb
  4. Add cardinality → how many rows on each side?

Step 2: Primary keys and foreign keys

Primary key (PK) — uniquely identifies each row in its own table

Foreign key (FK) — references the primary key of another table

The table that holds the foreign key is always on the many side of a relationship.

taxalist                    bird_observations
──────────────────          ──────────────────────────
species_id  (PK) ◄───────── species_id  (FK)
common_name                 survey_id   (FK)
asu_itis                    site_id     (FK)
                            bird_count
                            notes

One species in taxalist ← many observations in bird_observations

Step 4: Cardinality with crow’s foot notation

Crow’s foot symbols describe how many rows can participate on each side:

Symbol Name Meaning
——\| One and only one Exactly one row must match
——O\| Zero or one Optional: zero or one match
——< One or many At least one match required
——O< Zero or many Any number, including none

Example: bird_observations → taxalist

  • A bird observation identifies one and only one species ——| at the taxalist end
  • A species may have zero or many observations ——O< at the bird_observations end

The bird dataset ER diagram

bird_observations                surveys
─────────────────────────        ──────────────────────────
survey_id  (FK) O<────────|──── survey_id (PK)
site_id    (FK) O<───────────┐  site_id  (FK) O<────────|─┐
species_id (FK) O<──────┐    │                            │ │
bird_count               │    │  sites                    │ │
notes                    │    │  ──────────────────────   │ │
                         │    └─ site_id    (PK) ─────────┘ │
                         │       park_name                   │
                         │       park_district  ◄────────────┘
                         │       park_acreage
                         │
                         │    taxalist
                         │    ──────────────────────────
                         └─── species_id  (PK)
                              common_name
                              asu_itis

bird_observations sits at the center — three foreign keys, zero primary key columns of its own. Its identity is a compound key: survey_id + site_id + species_id.

Why does this matter before joining?
If you’re unclear on keys, you don’t know what the join is actually doing.

Choosing a join: start with your question

The join type should follow from what you need scientifically:

Question Join to use
I only want observations I can fully describe inner_join
I want all my observations, even if some metadata is missing left_join
I want to know what’s in both datasets, including gaps full_join
I want to check what won’t match before I commit anti_join

The most dangerous join is the one you choose without thinking.
A left_join when you needed an inner_join silently introduces NAs.
An inner_join when you needed a left_join silently drops data.

The most important question before every join

“How many rows do I expect in the result — and why?”

Rules of thumb:

  • Left join: result has ≥ rows than the left table (never fewer)
  • Inner join: result has ≤ rows than the smaller table
  • Full join: result has ≥ rows than the larger table
  • Any join: if a key matches multiple rows on the other side, you get row multiplication

Row multiplication is not always wrong — but it’s always worth noticing.

Row multiplication: a concrete example

Suppose bird_observations has 3 rows for site_id = "LI-W":

bird_observations (left)    sites (right)
────────────────────────    ─────────────────────
site_id  species  count     site_id  park_name
LI-W     BHCO     2         LI-W     Lindo Lake
LI-W     RWBL     5
LI-W     MODO     1

After left_join(by = "site_id"):

site_id  species  count  park_name
LI-W     BHCO     2      Lindo Lake
LI-W     RWBL     5      Lindo Lake
LI-W     MODO     1      Lindo Lake

3 rows in, 3 rows out — each observation gets its site’s metadata. This is correct and expected.

When row multiplication is a problem

Row multiplication becomes a problem when the right table also has multiple matches:

table_A (left)    table_B (right)
──────────────    ───────────────
id   value        id   category
X    10            X    cat1
X    20            X    cat2   ← two rows with same key!

After left_join(by = "id"):

id   value   category
X    10       cat1
X    10       cat2     ← value 10 appears twice!
X    20       cat1
X    20       cat2     ← value 20 appears twice!

2 rows in → 4 rows out. Your row count has doubled and your summary statistics are now wrong.

Take 5 minutes — type your answers in the chat

birds_subset: 3 rows
  site_id  species_id  bird_count
  LI-W     BHCO        2
  LI-W     RWBL        5
  NU-C     BHCO        1

Predict the row count for each of these joins:

  1. left_join(birds_subset, sites, by = "site_id")
  2. inner_join(birds_subset, taxalist, by = "species_id")

Practice 2 debrief

1. left_join(birds_subset, sites, by = "site_id")
→ 3 rows — all rows from birds_subset are kept; each gets its site’s metadata. No multiplication because sites has one row per site_id.

2. inner_join(birds_subset, taxalist, by = "species_id")
→ 3 rows — both BHCO and RWBL exist in taxalist, so all three observations match and are kept.

3. full_join(birds_subset, sites, by = "site_id")
→ 81 rows — 3 bird observation rows + 78 site rows that have no matching observations (NAs introduced for bird columns).

The habit: before every join, write down your expectation. If the result doesn’t match, stop and investigate.

Join syntax in R

All four mutating joins follow the same pattern:

# with pipe
left_table %>%
  left_join(y = right_table, by = "key_column")

# without pipe  
left_join(x = left_table, y = right_table, by = "key_column")

Always name the by argument explicitly — even when R would guess correctly.
It documents your intent and catches mismatches early.

# compound key: two columns must match
bird_observations %>%
  left_join(y = surveys, by = c("survey_id", "site_id"))

A new tool: filtering joins

Unlike mutating joins, filtering joins don’t add columns — they filter rows based on matches.

Function What it does
semi_join(x, y) Keep rows in x that have a match in y
anti_join(x, y) Keep rows in x that do not have a match in y

anti_join is your diagnostic tool: run it before committing to a join to see what won’t match.

# What observations have no matching site?
anti_join(bird_observations, sites, by = "site_id")

# What species have no observations?
anti_join(taxalist, bird_observations, by = "species_id")
