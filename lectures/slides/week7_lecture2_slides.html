Three ways a join can fail

Join failures are not always errors — R will happily return a result.
The failure is scientific: the result doesn’t mean what you think it does.

1. Silent data loss
An inner_join drops rows that don’t match — without warning.
You lose observations and may not notice.

2. Silent row multiplication
A key matches multiple rows on the other side.
Your result has more rows than expected; summaries are inflated.

3. Silent key mismatch
Keys that should match don’t — due to formatting, case, or encoding differences.
You get NAs or empty results where you expected data.

Failure 1: Silent data loss

Scenario: you have 595 bird observations and join to taxalist using inner_join.

birds_joined <- bird_observations %>%
  inner_join(y = taxalist, by = "species_id")

What could go wrong?
If any species_id in bird_observations doesn’t appear in taxalist, that observation is silently dropped.

How to check:

# Before joining: how many observations have no taxalist match?
anti_join(bird_observations, taxalist, by = "species_id")

If this returns any rows, you need to decide: is the missing species a data entry error, an unregistered species, or a legitimate gap?

Failure 2: Silent row multiplication

Row multiplication happens when the key you’re joining on is not unique in the right table.

surveys table — is survey_id unique?
survey_id  site_id  observer
S01        LI-W     Burns, J.
S01        LI-W     Burns, J.   ← duplicate row!
S02        NU-C     Morales, A.

Effect: every bird_observations row that matches S01 now appears twice.
Your total bird counts will be doubled for those surveys — but R returns no error.

How to check:

# Is survey_id unique in the surveys table?
surveys %>%
  count(survey_id) %>%
  filter(n > 1)

Practice 1 debrief

Two possible explanations for 612 rows when you expected 595:

Explanation A (problem): Some survey_id values in surveys appear more than once — duplicate rows created by data entry error. Each matched observation is multiplied.

Explanation B (expected): The join worked correctly, and you misunderstood the table structure — surveys has legitimate multiple rows per survey_id for some reason.

Code to investigate:

surveys %>% count(survey_id) %>% filter(n > 1)

Scientific problem: Explanation A. Duplicated survey records would inflate all downstream summaries — mean counts, totals, observer comparisons.

Failure 3: Key mismatches

Keys that should match often don’t — because of how data was entered.

Common culprits:

Problem Example
Inconsistent capitalization "LI-W" vs "li-w"
Leading/trailing whitespace "BHCO" vs "BHCO "
Different formats for the same value "J. Burns" vs "Josh Burns"
Encoding differences special characters, smart quotes

None of these produce an error. R joins on exact string equality.
"BHCO" and "BHCO " are different keys as far as R is concerned.

Detecting key mismatches with anti_join

anti_join is your first diagnostic. Run it in both directions:

# What's in bird_observations that has no match in taxalist?
anti_join(bird_observations, taxalist, by = "species_id")

# What's in taxalist that has no observations?
anti_join(taxalist, bird_observations, by = "species_id")

When anti_join reveals mismatches, inspect the unmatched keys:

# Look at the specific values that didn't match
anti_join(bird_observations, taxalist, by = "species_id") %>%
  distinct(species_id)

Then ask: Is this a real gap in the data, or a formatting problem I need to fix?

Fixing key mismatches before joining

Fix the formatting problem in the data before joining — and document it in your decision log.

# Trim whitespace from keys before joining
bird_observations <- bird_observations %>%
  mutate(species_id = str_trim(species_id))

taxalist <- taxalist %>%
  mutate(species_id = str_trim(species_id))

# Now join
bird_observations %>%
  left_join(y = taxalist, by = "species_id")

The decision log entry:
“Found leading/trailing whitespace in species_id in bird_observations (3 rows affected). Applied str_trim() prior to join. Checked with anti_join — 0 unmatched rows after cleaning.”

A diagnostic workflow for every join

Before joining:

  1. Verify your key is unique where expected
    table %>% count(key_col) %>% filter(n > 1)

  2. Run anti_join to find non-matching keys
    anti_join(left_table, right_table, by = "key")

  3. State your expected row count

After joining:

  1. Check actual row count against expectation
    nrow(result)

  2. Check for unexpected NAs in joined columns
    result %>% filter(is.na(joined_column))

  3. Document decisions in your decision log

Practice: Apply the diagnostic workflow

Take 5 minutes — work through this in your head or on paper

You have:

- bird_observations: 595 rows, species_id column

- taxalist: 58 rows, species_id column (one row per species)

You want to add common names from taxalist to your observations.

Walk through the diagnostic workflow:

  1. Which table’s key needs to be unique for this join to be safe?
  2. What would anti_join(bird_observations, taxalist, by = "species_id") tell you if it returns 12 rows?
  3. You run the join and get 595 rows. Is this reassuring? What else should you check?

Practice 2 debrief

1. Which key needs to be unique?
taxalist’s species_id must be unique — one row per species. If taxalist has duplicate species, you’ll get row multiplication. bird_observations can have repeated species_id values (multiple observations per species).

2. anti_join returns 12 rows:
12 observations in bird_observations reference species_id values not found in taxalist. These will lose common name information in a left_join, or be dropped entirely in an inner_join. Need to investigate: data entry error? Unregistered species?

3. 595 rows — what else to check?
Row count is correct. But check for NAs: result %>% filter(is.na(common_name)) — any NAs here correspond to those 12 unmatched observations from the anti_join.

The join decision framework

Step 1: What is your scientific goal?
→ Determines left vs. inner vs. full

Step 2: What does your data look like?
→ Check key uniqueness; run anti_join; state expected row count

Step 3: Execute the join

Step 4: Verify the result
→ Check row count; check for unexpected NAs; spot-check values

Step 5: Document
→ Which join, why, what you found, what you fixed

Steps 1 and 5 are the ones most people skip.
They are also the ones that matter most for reproducibility.
